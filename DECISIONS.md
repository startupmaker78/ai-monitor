## 2026-04-22 — Деплой — Yandex Cloud, не Vercel

**Решение:** прод-окружение Next.js хостим в Yandex Cloud (Serverless Containers или VM), а не на Vercel.

**Причины:**
1. Инфра (PostgreSQL, Object Storage) уже в Yandex Cloud, ru-central1. Vercel в США → +200-400ms latency на каждый запрос, критично для rrweb-трекера.

## 2026-04-22: Workflow миграций Prisma для Yandex Managed PostgreSQL

**Проблема:** `npm run prisma migrate dev` не работает с Yandex Managed PostgreSQL — у пользователя webmonitor нет прав на CREATE DATABASE для shadow database (стандартный механизм Prisma для сравнения схемы в dev-окружении).

**Решение — правильный workflow миграций:**

1. Изменить prisma/schema.prisma (добавить модель, поле, enum и т.д.)

2. Сгенерировать SQL миграцию БЕЗ shadow DB:
   ```
   npm run prisma migrate diff \
     --from-migrations prisma/migrations \
     --to-schema-datamodel prisma/schema.prisma \
     --script > /tmp/migration.sql
   ```
   Проверить содержимое /tmp/migration.sql глазами — не должно быть DROP TABLE без явного намерения, подозрительных ALTER и т.п.

3. Создать папку миграции вручную:
   ```
   mkdir -p prisma/migrations/<timestamp>_<descriptive_name>
   mv /tmp/migration.sql prisma/migrations/<timestamp>_<name>/migration.sql
   ```
   Где `<timestamp>` — формат YYYYMMDDHHMMSS, `<descriptive_name>` — snake_case, например `add_site_model` или `user_email_verified_field`.

4. Применить миграцию:
   ```
   npm run prisma migrate deploy
   ```

5. Обновить Prisma Client:
   ```
   npm run prisma generate
   ```

6. Проверить что всё в синхроне:
   ```
   npm run prisma migrate status
   ```
   → должно вернуть "Database schema is up to date!"

**Альтернатива на будущее (когда появится локальная БД):** настроить shadow database через Docker Postgres и указать shadowDatabaseUrl в prisma.config.ts — тогда `migrate dev` заработает как обычно.

**Применённые миграции:**
- `20260422000000_init_user_model` — первая модель User с enum UserRole (ADMIN, CONTRACTOR, OWNER)

## 2026-04-23: Модель привлечения — self-service для владельцев + партнёрская программа для подрядчиков

**Решение:** меняем модель с "closed beta через подрядчиков" на open self-service с опциональной партнёркой.

**Как работает:**
- Владелец сайта может САМ зарегистрироваться и оплатить подписку без приглашения.
- Подрядчик (например, дизайнер Тильды) подаёт заявку "Стать партнёром" → админ валидирует вручную → у подрядчика появляется кабинет с функцией приглашения клиентов.
- Клиент считается "приведённым подрядчиком" ТОЛЬКО если зарегистрировался по персональному invite-токену от этого подрядчика.
- Самостоятельно зарегистрированных клиентов привязать к подрядчику задним числом НЕЛЬЗЯ (защита от фрода).

**Причина изменения:** касдев с владельцами сайтов показал что они хотят самостоятельной регистрации, а не "приглашения от дизайнера".

**Последствия для архитектуры:**
- Нужны публичные страницы регистрации и оплаты для владельцев.
- Партнёрская программа — отдельный раздел с заявками и валидацией.
- Модель InviteToken остаётся, но теперь это дополнительный (не единственный) путь попадания в систему.

## 2026-04-23: Комиссия подрядчику — 50% навсегда, фикс

**Решение:** подрядчик, приведший клиента по своему invite-токену, получает 50% от каждого платежа клиента ПОЖИЗНЕННО (пока клиент платит).

**Альтернативы которые рассмотрели и отклонили:**
- Первый год 50%, потом 10% → сложнее считать, мотивация партнёра падает резко.
- Только первый год → короткая мотивация, подрядчики не будут поддерживать клиентов долгосрочно.
- Разный % для разных партнёров → слишком сложно для MVP, отложим.

**Причина:** простота для MVP, ясная мотивация партнёрам, легко считать.

**На будущее:** можно будет ввести разные % по сегментам (например, топовым партнёрам давать больше), но не сейчас.

## 2026-04-24: Условия запуска AI-анализа — обработка + кулдаун 7 дней

> **ЧАСТИЧНО УСТАРЕЛО 2026-04-27** — общая идея «обработка + кулдаун + лимит» сохраняется, но конкретные цифры и логика изменились: добавлено условие «цель в списке», кулдаун работает на пару (сайт, цель) а не глобально, длительность кулдауна зависит от тарифа (7 или 3 дня), лимит анализов по тарифам стал 4/12/24/48. См. запись «2026-04-27: Тарифная сетка переработана» ниже.

**Решение:** для запуска нового AI-анализа должны одновременно выполняться три условия:

1. Все рекомендации из топ-10 предыдущего анализа переведены в статус DONE или REJECTED (не NEW, не IN_PROGRESS)
2. С момента предыдущего анализа прошло минимум 7 дней
3. Не превышен месячный лимит по тарифу (Basic 1 / Pro 2 / Business 4)

**Обоснование:**

Условие 1 защищает от хаотичного использования:
- без него юзер запускает анализ, получает 15 рекомендаций, ничего не делает, завтра снова запускает — и у него 30 «висящих» карточек
- это убивает UX и обесценивает AI-рекомендации
- статус IN_PROGRESS считается «необработанным» — юзер должен явно довести до DONE или REJECTED

Условие 2 (7 дней) — продуктовое и экономическое обоснование:
- за 24 часа метрики не успевают измениться, вся аналитика metricsBefore/metricsAfter будет бессмысленной
- поле metricsAfter в схеме БД уже берётся «через 7 дней после DONE» — 7-дневный кулдаун синхронизируется с этим
- даёт юзеру время реально внедрить изменения, а не нажимать «Запустить» в спешке

Условие 3 — экономика тарифов:
- себестоимость одного анализа через Claude API ≈ 15-30₽, поэтому лимит важен для маржинальности
- цифры 1/2/4 дают маржу >95% на всех тарифах

**Важный нюанс для Business-тарифа:**

4 анализа в месяц / 7 дней кулдаун = теоретически ~4 анализа возможны, но сжато. Если юзер быстро обрабатывает рекомендации — успеет все 4. Если медленно — получит 2-3. Это **фича, не баг**: лимит — «максимум», фактическое количество зависит от темпа использования.

**UI-поведение:** кнопка «Запустить анализ» заблокирована если не выполнено хотя бы одно условие. Показываем пояснение — какое именно условие и что надо сделать:
- «Обработайте N оставшихся рекомендаций»

## 2026-04-25: Архитектура — модульный монолит, не микросервисы

**Решение:** MVP и ранняя стадия пилятся как модульный монолит (один Next.js проект с чётким разделением на модули), не микросервисы.

**Обоснование:**
1. У нас один разработчик (продакт + Claude Code) — микросервисы оправданы когда толпятся несколько команд.
2. Операционные расходы микросервисов (отдельные деплои, API gateway, service mesh, межсервисные логи) для MVP — гарантированное самоубийство.
3. Массовый тренд 2025-2026: значительная доля компаний, принявших микросервисы, возвращают часть функций обратно в монолит из-за сложности отладки и операционной нагрузки (см. отчёты CNCF, статьи в InfoQ, DZone). Конкретные цифры варьируются от источника к источнику — тренд важнее цифр.
4. AI-ассистенты (Claude Code) эффективнее работают с монорепо — весь контекст в одном месте.
5. Сетевая латентность между сервисами (10-50ms на вызов) критична для rrweb-трекера, который шлёт данные каждые 30 сек.

**Модульность обеспечиваем структурой** (точные пути см. в ARCHITECTURE.md → "Структура репозитория"):
- Отдельные зоны UI под роли: `app/(dashboard)` для владельцев, `app/(contractor)` для подрядчиков, `app/(admin)` для админки
- Отдельные группы API-эндпоинтов по функциональным областям: auth, tracking, metrika, analysis, webhooks (ЮКасса), clients
- Вспомогательные модули в `lib/`: prisma, claude, metrika, yookassa, resend, storage, crypto — по одному на внешнюю интеграцию или кросс-проектную утилиту
- Межмодульные вызовы — только через чёткие интерфейсы (функции, типы), без прямых обращений в приватные куски чужого модуля

**Когда пересмотреть:** если у нас 5+ разработчиков ИЛИ 100k+ строк кода ИЛИ один компонент стал узким местом по производительности.

**Альтернативы которые рассмотрели:**
- Микросервисы с первого дня — отклонено по причинам выше
- Чистый монолит без модульности — отклонено, это путь к спагетти-коду через полгода

## 2026-04-27: «Цель анализа» как сущность — модель AnalysisTarget

**Решение:** вводим в схему БД новую таблицу AnalysisTarget — это URL страницы сайта, по которой пользователь может запускать AI-анализ. Каждый Analysis привязан к конкретному AnalysisTarget через targetId.

**Логика:**
- Цель = один URL (например, `https://site.ru/pricing`). Не паттерн, не группа URL — на MVP только конкретные URL.
- Цели создаёт владелец сайта в кабинете. Лимит активных целей зависит от тарифа.
- Кулдаун между анализами считается на пару (siteId, targetId), не глобально по сайту.
- Условие «обработать топ-10» применяется к последнему анализу этой же цели — анализы других целей не блокируют.
- Лимит анализов в месяц — суммарный по сайту (любые цели в любой комбинации).
- При архивации цели (`archivedAt`) она исчезает из UI выбора при запуске анализа, но прошлые Analysis остаются доступны в истории.

**Обоснование выбора «один URL» а не «паттерн URL»:**
- Проще для MVP (нет ambiguity «совпадает ли /products/123 с /products/*»).
- Понятнее в UI (юзер указывает конкретный URL, видит конкретный URL).
- Можно добавить паттерны позже если будет запрос (особенно от интернет-магазинов с тысячами товарных страниц).

**Технические детали:**
- AnalysisTarget.url — string, без уникальности (юзер может теоретически добавить дубль; обработка дублей — на уровне UI с предупреждением).
- AnalysisTarget.archivedAt nullable — soft delete, потому что Analysis.targetId ссылается на цель и история должна сохраняться.
- Analysis.targetId NOT NULL — каждый новый анализ обязательно привязан к цели; legacy-данных нет (модель вводится одновременно с AnalysisTarget на этапе 0.c.5).

**Связанные изменения:**
- ARCHITECTURE.md (коммит bd2c6da): схема модели AnalysisTarget, изменения в Analysis, секция «Условия запуска нового анализа».

## 2026-04-27: Модель Subscription и SubscriptionEvent — решения по этапу 0.c.4

**Решение:** реализуем биллинговый слой через две таблицы — `Subscription` (одна запись на Owner) и `SubscriptionEvent` (immutable лог всех изменений подписки, не только финансовых).

### Subscription — одна запись на Owner за всю историю

`Subscription.ownerId` объявлен `@unique`. При апгрейде/даунгрейде/продлении меняем поля той же записи, а не создаём новую. История тарифов восстанавливается через `SubscriptionEvent`.

**Альтернатива которую отклонили:** хранить историю тарифов как series записей в Subscription с полями `validFrom`/`validTo`. Отклонено, потому что:
- При каждом обращении к "текущей подписке" пришлось бы делать `WHERE validTo IS NULL` — лишняя сложность
- История уже хранится в SubscriptionEvent — дублирование

### SubscriptionEvent, а не PaymentEvent

Логируем не только денежные события, но и любые изменения подписки: апгрейды, даунгрейды, отмены через UI без платежа, истечение периода. Без этого нельзя восстановить полную историю тарифов клиента — например, "юзер отменил подписку" без платежа не оставит следа.

**Технически:** поля `amount`, `currency`, `yookassaPaymentId` сделаны nullable — для не-денежных событий они пустые. Для бухгалтерской выгрузки фильтр `WHERE amount IS NOT NULL` отдаёт только платежи.

`yookassaPaymentId` — `@unique`, защита от двойной обработки вебхука.

### analysesUsedThisPeriod при смене тарифа НЕ сбрасываем

При апгрейде/даунгрейде счётчик использованных анализов в текущем периоде остаётся как есть — защита от абьюза по схеме BASIC→STANDARD→BASIC (юзер мог бы за месяц получить 4+12+4 = 20 анализов вместо 4 на Базовом).

**Последствие:** если юзер потратил 8 анализов на STANDARD и сделал даунгрейд на BASIC (лимит 4) — анализы заблокированы до начала следующего платёжного периода. Это корректное поведение, не баг. Логика проверки лимита — в коде, не в схеме.

### Период биллинга — от даты подписки

Подписался 14-го числа → следующий период начинается 14-го следующего месяца. Не календарный месяц. Расчёт через `date-fns` (`addMonths`), который корректно обрабатывает кейсы типа "31 января → 28/29 февраля".

Поля `currentPeriodStart` и `currentPeriodEnd` хранятся в Subscription, обновляются при каждом успешном продлении. Сброс `analysesUsedThisPeriod` происходит только при создании события `PAYMENT_SUCCEEDED` типа RENEWAL.

### Триал на MVP не делаем

В enum `SubscriptionStatus` нет TRIAL. Когда понадобится — добавим миграцией.

### Enterprise тариф на MVP не делаем

В enum `SubscriptionTier` нет ENTERPRISE и в `Subscription` нет поля `customLimits Json?`, хотя это упоминается в PRODUCT.md и в ARCHITECTURE.md как стратегическое направление. Причина: Enterprise — ручной B2B-процесс с переговорами, на MVP клиентов не будет. Когда появится первый — добавим миграцией ENTERPRISE в enum и поле customLimits.

## 2026-04-27: Модель «Бюджеты сессий на цель» — переход с кулдауна на распределение лимита сессий

**Решение:** меняем модель регулирования AI-анализов. Раньше частоту запусков ограничивали два механизма — кулдаун в днях (7 для BASIC/STANDARD, 3 для PROFESSIONAL/CORPORATE) и месячный лимит анализов. Теперь оставляем только месячный лимит анализов (4/12/24/48), а вместо кулдауна вводим **бюджеты сессий на каждую цель** — юзер сам распределяет общий лимит сессий тарифа между AnalysisTarget'ами, и анализ запускается когда у конкретной цели накоплено ≥100 сессий.

### Что было не так с предыдущей моделью

В исходной концепции (см. записи от 2026-04-23 и 2026-04-27 про тарифную сетку) лимит сессий был «общим по сайту» — просто счётчиком сессий за месяц. А кулдаун в днях защищал от спама анализов. Эта модель имела две проблемы:

1. **Низкотрафичные страницы получали мусорный анализ.** Если на странице «О компании» 30 сессий в неделю, по правилу «прошло 7 дней — можно анализировать» Claude получал бы 30 сессий и выдавал бы галлюцинации. Качество рекомендаций не масштабировалось.

2. **Стоимость одного анализа была непредсказуемой.** Юзер на BASIC мог запустить анализ на 1000 сессиях главной страницы — расход токенов Claude варьировался в разы между анализами. Экономика тарифа плыла.

3. **Кулдаун был эвристикой**, не отражающей реальной готовности страницы к новому анализу. На высокотрафичной главной за 7 дней могло набраться 5000 новых сессий — кулдаун избыточен. На низкотрафичной — за 7 дней набралось 50 сессий, но по таймеру можно — и анализ выходит мусорный.

### Новая модель: бюджет сессий на цель

Юзер при создании AnalysisTarget указывает `sessionsBudget` — потолок сессий, которые цель должна накопить перед анализом. Минимум 100 (защита от мусорных анализов), максимум — оставшийся свободный баланс тарифа. Сумма бюджетов всех активных целей не может превышать `Subscription.sessionsLimit`.

Скрипт собирает сессии: при закрытии каждой сессии сервер определяет на какой странице посетитель провёл больше всего времени; если страница совпадает с url одной из активных целей сайта — счётчик `sessionsCollected` этой цели увеличивается на 1. Когда `sessionsCollected ≥ 100` — цель в статусе `READY`, кнопка «Запустить анализ» активна.

После запуска анализа цель переходит в `ANALYZING` → `COMPLETED`. В текущем периоде повторный анализ этой же цели невозможен. Сброс происходит при обновлении периода Subscription (счётчики обнуляются, бюджеты сохраняются).

### Принятые решения по поведению модели

Все решения зафиксированы по результатам опросника:

1. **Сессия посетителя засчитывается ровно одной цели** — той, на странице которой он провёл больше всего времени за сессию. Не «первой посещённой», не «последней» — а максимальной по длительности. Технически: при `endedAt` сервер анализирует rrweb-таймлайн URL, выбирает максимум среди тех URL, что есть в активных целях сайта (status ∈ {ACTIVE, READY}).

2. **Минимум 100 сессий** — это и минимальный `sessionsBudget` (нельзя поставить цель с потолком меньше 100), и минимум для запуска анализа (`sessionsCollected ≥ 100`).

3. **Сумма бюджетов не может превышать `sessionsLimit` тарифа** — UI блокирует сохранение, если сумма аллокаций больше лимита. Защита от ситуации «накопилось 2500 сессий, но они «забронированы» под 3000 сессий бюджета».

4. **Параллельные анализы разрешены** — юзер может запустить анализ нескольких целей одновременно (если у каждой накоплено ≥100). Ограничение только по общему лимиту анализов в месяц.

5. **Архивация цели возвращает бюджет на свободный баланс**, если по этой цели ещё не запускался анализ. Если анализ был — бюджет уже потрачен и не возвращается. Накопленные `sessionsCollected` при архивации сгорают (счётчик зануляется).

6. **«Отменить сбор оставшихся» после запуска анализа** — кнопка появляется сразу при переходе цели в ANALYZING (даже пока Claude ещё думает). Юзер может нажать — `sessionsBudget` цели обрезается до фактического `sessionsCollected` на момент анализа, разница возвращается на свободный баланс.

7. **При обновлении периода (платёжного):** счётчики `sessionsCollected` всех целей обнуляются, цели в статусе COMPLETED → ACTIVE (можно повторно), бюджеты сохраняются как были. Цели в ARCHIVED остаются как есть.

8. **Если подписка истекла (юзер не оплатил):** трекинг-скрипт перестаёт принимать сессии — `/api/tracking/collect` возвращает 402 (или 403). Старые анализы и накопленные данные доступны read-only. При новом платеже всё разморозится с нуля.

9. **Месячный лимит анализов остаётся** (4/12/24/48). Это защита экономики Claude — один анализ это реальные деньги в облаке. Хотя на практике лимит сессий и так ограничивает кейсы (если 1000 сессий распределены по 4 целям по 250, то будет ≤4 анализа), он режет редкий граничный кейс — много мелких целей по 100 сессий.

### Что изменилось в схеме БД (этап 0.c.5)

- `Subscription`: новые поля `sessionsLimit Int` и `sessionsAllocated Int`. Денормализованный счётчик аллоцированных сессий — для быстрых проверок UI без агрегата при каждом запросе.
- `AnalysisTarget`: новые поля `sessionsBudget Int` (минимум 100), `sessionsCollected Int @default(0)`, `status AnalysisTargetStatus`. Новый enum `AnalysisTargetStatus { ACTIVE | READY | ANALYZING | COMPLETED | ARCHIVED }`.
- `Session`: новое поле `analysisTargetId String?` — FK на AnalysisTarget с `ON DELETE SET NULL`. Проставляется при закрытии сессии.

### Что отменяется

- **Кулдаун в днях между анализами одной цели** — больше не используется. Запись «2026-04-27: Тарифная сетка переработана» помечена как частично отменённая в этой части.
- **Поле `Subscription.sessionsLimit` в значении «общий счётчик сессий за месяц»** — теперь это «общий бюджет на распределение между целями». Семантика поменялась.

### Альтернативы которые рассмотрели и отклонили

- **«Сессия засчитывается всем посещённым целям»** — отклонено: одна сессия = одна единица бюджета, иначе бюджеты теряют смысл (одна сессия посетителя могла бы тратить 3 единицы из разных целей).
- **«Засчитывается первой/последней посещённой»** — технически проще, но продуктово менее честно. Юзер мог зайти на /pricing, потом случайно кликнуть на /about; считать сессию за /about неправильно.
- **`sessionsAllocated` высчитывать на лету через SUM(sessionsBudget)** — отклонено: считается на каждом запросе UI (проверка «можно ли создать ещё одну цель»), денормализованный кэш быстрее. Поддерживаем актуальность через триггеры в коде.
- **Кулдаун оставить + добавить бюджеты сверху** — отклонено: два механизма блокировки запуска избыточны и запутывают юзера.

### Связанные изменения

- PRODUCT.md: переписаны разделы «AI-анализ», «Управление целями анализа», таблица тарифов (убрана колонка «Кулдаун»).
- ARCHITECTURE.md: обновлены блоки `Subscription`, `AnalysisTarget`, `Session`, таблица «Лимиты по тарифам», секция «Условия запуска нового анализа».
- Этап 0.c.5: миграция добавит новые поля и enum AnalysisTargetStatus.

## 2026-05-03 — eventsCount on Session не идемпотентен на ретрае (acceptable)

**Контекст:** Этап 4, коммит 4/8.

Session.eventsCount инкрементится через Prisma `{ increment }` на каждый
upsert update. На ретрае одного packetIndex (network race на клиенте,
fetch не получил ответ — retry) счётчик дублируется.

**Решение:** acceptable на MVP. Не фиксим в этом коммите.

**Почему acceptable:**
- eventsCount это telemetry-поле, не billing
- Реальный контент сессии в Object Storage идемпотентен (putJson
  перезаписывает по ключу sessions/{siteId}/{sessionToken}/{N}.json)
- AI-анализ читает события из Object Storage, eventsCount не использует
- UI /dashboard/sessions может показать примерное число — не критично

**Когда фиксим:** одновременно с введением
Subscription.sessionsCollected к тарифным лимитам (эта модель — на
будущем этапе после MVP, в roadmap отсутствует). Решение тогда:
отдельная таблица SessionPacketReceipt с UNIQUE (sessionToken,
packetIndex), `INSERT ... ON CONFLICT DO NOTHING`.

**Update 2026-07-08:** collect route получил transient DB retry
(withDbRetry, 1 повтор на разрыве pg-соединения) — см. запись
«collect: transient DB retry» ниже. Это ПОВЫСИЛО частоту сценария
двойного eventsCount: разрыв между `COMMIT` и получением ACK клиентом
Prisma → повтор `$transaction` попадает в SUBSEQUENT-ветку
(createMany count=0, session уже существует), которая делает
`update({eventsCount: {increment: len}})` поверх уже установленного
в create `eventsCount = len`. sessionsCollected при этом не
дублируется (гейт `isFirstPacket && validatedTargetId`). Косметика в
telemetry-поле по-прежнему acceptable, но учесть, что теперь
триггерится не только клиентским network-retry (у нас нет), но и
серверным withDbRetry на редком post-commit disconnect'е.

**Update 2026-07-09 — РЕАЛИЗОВАНО (вариант B).** Предзаложенное здесь
решение (таблица `SessionPacketReceipt` с UNIQUE (sessionToken,
packetIndex) + `INSERT ON CONFLICT DO NOTHING`) реализовано —
eventsCount теперь идемпотентен по пакету. Больше НЕ acceptable-долг,
а закрыто. См. запись «2026-07-09 — eventsCount идемпотентность
(вариант B, миграция)» ниже.

## 2026-05-03 — analysisTarget matching полагается на синхронизированные клиентские часы (acceptable)

**Контекст:** Этап 4, коммит 5/8. Алгоритм lib/analysis-target-matcher.ts → computeDominantUrl().

Алгоритм использует rrweb-event timestamps (Date.now() у клиента) для
расчёта длительности на каждом URL. На финальном пакете последняя
длительность = sessionEndedAt - lastMeta.ts, где sessionEndedAt это
now() сервера.

**Проблема:** если у клиента сильный clock skew (часы врут на часы/дни),
расчёт поплывёт: либо длительность сильно завышена, либо последний URL
получит 0 (если client.ts > server.now).

**Решение:** acceptable на MVP. Не фиксим в этом коммите.

**Почему acceptable:**
- Большинство клиентов имеют корректное время через NTP
- Антифрод не наша зона на MVP
- Math.max(0, end - start) защищает от отрицательных длительностей
- Найден на синтетическом тесте с 2023→2026 timestamps; реалистичная
  ошибка часов на 1-2 минуты — несущественна

**Когда фиксим:** при необходимости. Решение: использовать server-side
receivedAt (уже пишется в Object Storage в коммите 4/8) для расчёта
времени между пакетами вместо client ts. Расхождение между receivedAt
последнего пакета и предыдущей Meta события — корректная длительность.

## 2026-05-05 — Hotfix 4: AnalysisTarget.budgetSpent — правильная модель бюджета

**Контекст:** Этап 6, четвёртый hotfix к коммиту 6.1. После
деплоя hotfix 2 обнаружен бизнес-баг: юзер архивировал цель
status=ARCHIVED с sessionsCollected=523 — бюджет 600 вернулся
на свободный баланс. Это эксплойт: можно крутить "анализ →
архив → ещё анализ" бесконечно за один тариф.

**Корень проблемы:** в hotfix 1-2 мы пытались косвенно определить
"бюджет потрачен" через комбинацию status и archivedAt. Сложная
логика, неочевидные edge cases.

**Правильное решение:** явное поле AnalysisTarget.budgetSpent:
Boolean. Семантика проста — "AI-анализ был запущен и бюджет
потрачен навсегда".

**Жизненный цикл budgetSpent:**
- default false (при создании цели)
- переключается в true при запуске анализа (status: ACTIVE/READY
  → ANALYZING) — реализуется в коммите 6.4
- НИКОГДА не снимается обратно

**Логика sessionsAllocated:**
- Сумма sessionsBudget где (archivedAt IS NULL) ИЛИ (budgetSpent=true)
- Архивация ACTIVE/READY цели где budgetSpent=false → бюджет
  освобождается (юзер передумал, не успел запустить анализ)
- Архивация цели где budgetSpent=true → бюджет остаётся занятым
  навсегда (анализ уже потрачен)

**Data migration:** UPDATE AnalysisTarget SET budgetSpent=true
WHERE sessionsCollected > 0. Закрывает баг для существующих
записей.

**Упрощение:** archiveTarget теперь всегда ставит status=ARCHIVED
без conditional логики. Семантика чистая — ARCHIVED = "юзер
удалил цель", budgetSpent = отдельный финансовый флаг.

**TODO для коммита 6.4:** при переходе AnalysisTarget.status
ACTIVE/READY → ANALYZING — обязательно ставить budgetSpent=true
в той же транзакции.

**Альтернативы не выбраны:**
- "Не возвращать бюджет вообще никогда" — нарушает UX, юзер
  создал цель и не может передумать без потери денег
- "Расширить status enum: SPENT_ARCHIVED" — дублирует семантику,
  sql query усложняется

**Урок: data migration через WHERE status IN, не sessionsCollected**

Первая попытка использовала `WHERE sessionsCollected > 0` как
proxy для "был запущен анализ". Это false proxy: ACTIVE цели
тоже накапливают sessionsCollected (это их жизненный цикл —
копят до запуска анализа). Корректная миграция использует
`WHERE status IN ('ANALYZING', 'COMPLETED')` плюс отдельное
условие для ARCHIVED с sessionsCollected > 0 (те что были
COMPLETED до архивации).

Зафиксировано в корректирующей миграции
20260505224443_fix_budget_spent_for_active_targets.

**Принцип на будущее:** при data migration предпочитать
условия по explicit status enum, а не по count полям.
Status — точная семантика, count — derivative.

## 2026-05-05 (поздно вечером) — Hotfix 5: финальная модель архивации

**Контекст:** После 4 hotfix-ов модели бюджета (header text →
COMPLETED archive → navigation → budgetSpent flag) обнаружен
второй эксплойт: юзер с status=ACTIVE может собрать сессии,
архивировать (получить budget назад), создать новую цель, снова
собирать и т.д. Нагружает инфру (Object Storage) бесплатно.

**Финальная модель (правильная):**

Архивация разрешена ТОЛЬКО:
1. status IN (ACTIVE, READY) И sessionsCollected = 0 — юзер
   передумал до сбора, возвращается весь budget
2. status = COMPLETED — анализ был запущен и завершён,
   возвращается (budget - sessionsCollected)

Архивация ЗАПРЕЩЕНА:
- status IN (ACTIVE, READY) И sessionsCollected > 0 — "Сначала
  запустите анализ"
- status = ANALYZING — "Анализ идёт"

**sessionsAllocated формула:**
- Активные (archivedAt IS NULL): полный sessionsBudget
- Архивированные: только sessionsCollected (что реально
  использовано до архивации)

**Поле budgetSpent удалено.** Семантика "бюджет потрачен"
теперь живёт в простой формуле без флагов.

**Почему именно так:**
- Сессии собраны = ресурс израсходован, должен быть проанализирован
- Если юзер передумал ДО сбора — без проблем, возврат

## 2026-05-08 — Архитектурное решение: трекер пишет ТОЛЬКО на 
зарегистрированных target URLs

**Контекст:** Подключили трекер к nolim.cc. На 40-минутной сессии 
получили ~15000 events / 7-10 MB rrweb данных в S3. Поднялся вопрос 
объёмов и того, что мы вообще пишем.

**Логическое доказательство необходимости pivot'а (от Лёши, ночь 8 
мая):**
1. Юзер платит за анализ конкретного target (URL страницы)
2. Рекомендации даются ТОЛЬКО по target'у (иначе ломается монетизация 
   — клиент за один тариф получит анализ всего сайта вместо одной 
   страницы)
3. Записываем events с других страниц (не target)
4. Этими events мы НЕ пользуемся в анализе
5. → они мусор: занимают S3, тратят bandwidth, увеличивают latency 
   pre-processor'а
6. → писать мусор архитектурно неверно

**Решение:** Трекер записывает rrweb-события ТОЛЬКО когда юзер 
находится на странице, входящей в список зарегистрированных 
AnalysisTarget URLs владельца.

**Что это меняет:**
- Workflow: target известен ДО записи, computeDominantUrl 
  теряет смысл (matcher → simple filter)
- Tracker config: трекер должен знать список target'ов сайта 
  (новый API endpoint /api/sites/{id}/targets, кешируется в 
  трекере на N минут)
- Privacy: больше НЕ пишем PII с логин/кабинетов клиентов 
  (152-ФЗ-friendly)
- S3 cost: ожидаемое падение в 5-7x
- "Ценностная упаковка" продукта чёткая: одна цель = одна страница 
  с записью

**Что теряем:**
- "Journey context" (откуда юзер пришёл, куда ушёл с target'а) — 
  но мы и не использовали его в рекомендациях, так что чистая 
  оптимизация
- Возможность переанализировать сессию под другой target 
  ретроактивно — но это никогда не было заявленной фичей
- Полный rrweb-плеер пути юзера (этап 9) — становится 
  фрагментарным. Но плеер был запланирован "минимальная версия" 
  и под отдельный target — без потери ценности

**Реализация — план на 8 мая:**
1. Discovery промпт: как трекер узнаёт список target'ов, что 
   делать при no-targets, SPA vs MPA, cache strategy
2. Pre-migration если нужны новые поля
3. Implementation коммиты (estimated: 2-3 коммита, ~1 день)

**Следующие шаги перед релизом MVP** (не блокеры этого решения, но 
связанные):
- Sampling mousemoves в rrweb-config: 50ms → 100-200ms (доп 
  оптимизация)
- Hard limit 30k events per session (drop overflow) — защита от 
  пограничных кейсов
- Замер pre-processor производительности после реализации

## 2026-05-08 (полдень) — Debug session: ложная тревога про cron-trigger + learnings по yc CLI

**Контекст:** YC Timer Trigger `finalize-stale-sessions` (id `a1ssv60ll57u264na868`) казался сломанным после деплоя 09:22 UTC ревизии `f758ca4`. Симптом: `yc logging read --since 4h --limit 5000` показывал newest=`09:21:00 UTC` при текущем 09:44 UTC, что выглядело как «триггер не тикает 23 минуты». При сужении окна до `--since 1h` + `--filter 'message:"cron-finalize"'` нашлись тики `09:31`, `09:46` — триггер работал штатно. Триггер не пересоздавал, конфигурацию не менял.

**Learnings (yc CLI):**

1. **`yc logging read --since X --limit N` обрезает по limit *старейших* записей в окне.** Если за окно >N events — `--limit 1000` или даже `--limit 5000` забивается старыми, newest в выдаче выглядит замороженным. На staging при активном трекере (300+ events/min от nolim.cc) `--since 30m` забивает любой реалистичный лимит.
   **Как правильно**: узкое окно (`--since 1m`/`5m`/`30m`) + server-side `--filter` (например `--filter 'message:"cron-finalize"'`) + `--resource-types serverless.container`. Default sort ascending — `--limit 1` даёт **самую старую** запись окна, не самую свежую.

2. **YC Timer Trigger cron-expression `*/15 * * * ? *` тикает каждые 15 минут от `created_at` триггера**, не от ровных минут :00/:15/:30/:45 часа. Триггер созданный в `08:43:56 UTC` даёт тики на 08:46, 09:01, 09:16, 09:31, 09:46 (initial offset ~3 мин + каждые 15). При создании нового триггера сначала проверить фактическое расписание через первые 2-3 тика, не предполагать.

3. **`yc config list` всегда выводит IAM-token в первой строке** (zero-effort leak в transcripts/чаты). Использовать `yc config get <field>` (например `yc config get folder-id`) либо фильтровать `yc config list 2>&1 | grep -v '^token:'`. См. также TODO.md → Безопасность 2026-05-08.

4. **`yc serverless trigger get` всегда выводит CRON_SECRET в `payload`** (plaintext). Маскировать через `--format json | jq 'del(.timer.invoke_container_with_retry.payload, .rule.timer.invoke_container_with_retry.payload)'` (поле дублируется в `.timer` и `.rule.timer`).

**Урок на архитектурном уровне:** debug staging-инфраструктуры через CLI без structured-observability (Grafana/dashboard для invocations + error rate триггеров) приводит к ложным тревогам и трате времени на расследование. После MVP — поднять Yandex Monitoring dashboard с метриками триггеров (`trigger.invocations`, `trigger.errors`) чтобы за один взгляд видеть, тикает ли cron.

## 2026-07-08 — Трекер: изоляция FullSnapshot + фиксы порядка эмита

**Контекст:** сессии academy.nolim.cc отдавали в S3 только packet idx=1..7 (только type=3 IncrementalSnapshot, ни одного FullSnapshot type=2, ни одного Meta type=4). Плеер = белый экран (нет initial DOM). Замерили FullSnapshot реального сайта — **~2.92 MB**, что при склейке с сопутствующими инкрементами (200/packet) уверенно превышало `MAX_BODY_BYTES=3 MiB` на collect → 413 от YC-платформы **до контейнера** (в контейнерных логах ничего). Отсёкся именно первый packet.

**Решение** — стек из трёх клиентских правок в `tracker-src/`:

1. **`buffer.ts` handleVisibilityChange: `flushFinal()` → `flush()`** — visibilitychange (переключение вкладки в background) больше не финализирует сессию. Раньше `flushFinal` защёлкивал `finalSent=true` навсегда → любое tab-switching до первого FullSnapshot убивало сессию. Финал теперь **только на pagehide**. Побочка задокументирована в TODO (проверить надёжность).

2. **`rrweb-config.ts` recordAfter: `'DOMContentLoaded'`** — снимает дефолт rrweb 'load'. Если `record()` вызвана при `readyState==='loading'` (а у нас — после `await checkShouldRecord`), FullSnapshot не откладывается до `window.load`, а срабатывает сразу после DCL. Commit `e85e056`, revision `bba9p56v159c90k2gr2m`.

3. **`buffer.ts add() — изоляция FullSnapshot**: любой event с `type===2` уходит собственным packet'ом (закрыть накопленное `flush()` → push snapshot → немедленный `flush()`). Meta type=4 rrweb эмитит чуть раньше FullSnapshot тем же takeFullSnapshot и она осядет в предыдущем flushed packet'е — порядок Meta→FullSnapshot по packetIndex сохраняется. Изоляция также покрывает periodic snapshots от `checkoutEveryNms=5min`. Commit `ca5f4e7`, revision `bbae67mgqpdr36aossfh`.

**Почему изоляция, а не chunking:** chunking rrweb-events через границу packet'а перегружает клиент и требует reassembly на плеере. Изоляция дешевле — один event в packet, тело ~= размер snapshot'а. FullSnapshot 2.92 MB укладывается в 3 MiB cap **без запаса** (93% cap); при росте контента academy — снова 413. Долгосрочный фикс — gzip тела (см. TODO P1).

## 2026-07-08 — should-record: try/catch + transient DB retry, 503 вместо uncaught 500

**Контекст:** роут `GET /api/tracking/should-record` при первом запросе после idle/cold-start контейнера отдавал **HTTP 500 без CORS-заголовков**. Клиентский трекер fail-closed → запись не стартует, юзер не понимает почему. Единственная ошибка в container-логах: `Error: Connection terminated unexpectedly` — pg driver, stale connection в Prisma-пуле (Yandex Managed PostgreSQL рубит idle TCP, singleton держит их как «живые»). Роут был **без try/catch**.

**Решение:** локальный `withDbRetry<T>` + предикат `isTransientDbError` в самом файле роута. Транзиентные маркеры message: `Connection terminated unexpectedly`, `Server has closed the connection`, `ECONNRESET`. Транзиентные codes: `P1001`, `P1017`, `ECONNRESET`. Логика — **ровно 1 повтор** после ~120ms sleep; non-transient сразу пробрасывается; повтор не помог → catch отдаёт **HTTP 503 `{record:false, reason:"db_unavailable"}` + CORS** (не 500, не заглушенный 200).

**Почему 1 повтор:** первый throw заставляет pg-pool выбросить битое соединение — второй вызов идёт через свежее. Больше не ретраить, иначе замаскируем реальный DB-даун (не 5xx на сотнях запросов). Логика идентична собранной ниже в `lib/prisma.ts` — TODO переключить.

## 2026-07-09 — gzip сжатие тела пакетов (octet-stream + magic-детект)

**Проблема:** FullSnapshot реальной страницы academy.nolim.cc ≈ **2.92 MB** = 93% от collect-cap 3 MiB. Изоляция снапшота в отдельный packet (2026-07-08, commit `ca5f4e7`) спасала на текущем контенте, но при любом росте DOM → снова 413 от YC-платформы **до** контейнера. Цель gzip — снять лимит навсегда + побочно срезать клиентский трафик и байты в S3.

**КЛЮЧЕВАЯ НАХОДКА (поведение YC-платформы):** нельзя слать gzip с заголовком `Content-Encoding: gzip`. Serverless-proxy **контейнера** прогоняет такое тело через UTF-8-нормализацию и заменяет невалидные UTF-8 байты на U+FFFD: байт `0x8b` (второй байт gzip-magic) → `ef bf bd`, тело разрушается безвозвратно. Проверено TEMP эхо-роутом со сравнением sha256 отправленного и принятого:
- `Content-Encoding: gzip` + `application/json` → sha разошёлся, `first8Hex = 1f efbfbd 08…`, gunzip падает. Природа — **utf8-mangle** (НЕ base64: гипотеза base64 отвергнута, `base64→gunzip` тоже false).
- тот же gzip как `application/octet-stream` **БЕЗ** `Content-Encoding` → sha совпал, `first8Hex = 1f8b08…`, gunzip ok. **Проходит целым.**
- Искажает именно **контейнерный proxy**, не API Gateway: container-direct (bypass Gateway) даёт тот же результат.
- Лимит **3.5 MiB считается по СЖАТОМУ телу на проводе** (эмпирически: сырые 4.77 MB → 413 `ProxyIntegrationError (3670016)`; gzip 4.8 KB с распаковкой в 4.77 MB → проходит). gzip реально помогает против лимита.

**РАБОЧАЯ СХЕМА:**
- **Клиент** ([tracker-src/transport.ts](tracker-src/transport.ts), `sendPacket`): шлёт `gzip(json)` как `Content-Type: application/octet-stream` **БЕЗ** `Content-Encoding`. Сжатие через `CompressionStream('gzip')`.
- **Сервер** ([app/api/tracking/collect/route.ts](app/api/tracking/collect/route.ts)): детектит gzip **по magic-байтам** (`buf[0]===0x1f && buf[1]===0x8b`), НЕ по заголовку → `zlib.gunzipSync(buf, { maxOutputLength: MAX_INFLATED_BYTES })`; иначе `buf.toString('utf8')` (plain). Добавлен `export const runtime = "nodejs"`.
- **Два лимита:** `MAX_WIRE_BYTES = 3 MiB` (входное тело — сжатое или сырое), `MAX_INFLATED_BYTES = 8 MiB` (распакованное). Anti-zip-bomb через `maxOutputLength`: обрывает распаковку на пороге, НЕ аллоцируя весь выход — memory-safe, а не post-hoc проверка.
- S3 по-прежнему хранит packet.json **разжатым** — gzip только на transport.

**Клиентские страховки:**
- Feature-detect `CompressionStream` (нет в Safari <16.4, Firefox <113, Chrome <80) → без него plain-путь ровно как раньше.
- **Fallback на plain при любом не-2xx** ответе на gzip-отправку: ровно **1 повтор** тем же пакетом plain'ом (`application/json`). Если сервер по любой причине не принял gzip — запись не теряется. `sendFinalPacket`/beacon не трогали (sentinel `events=[]` крошечный, уходит plain через beacon).

**Регрессия и урок (two-phase deploy):** первый деплой (commit `ccc856f`) ставил `Content-Encoding: gzip` — сервер отвечал 400 `invalid_encoding`, а клиент **без fallback** дропал пакет → запись сломалась для современных браузеров (у которых `CompressionStream` есть; старые/beacon на plain работали). Откачено revert'ом (`ccc856f` → `1d799f8`), причина найдена эхо-роутом, схема переделана на octet-stream + magic. **Уроки:**
1. Сервер (принимает и gzip, и plain) деплоить **ПЕРВЫМ**, клиент **ВТОРЫМ**: сервер backward-compat, клиент зависит от сервера.
2. Клиентский plain-fallback на не-2xx — обязательная страховка: даже при нарушении порядка деплоя или отказе сервера запись самолечится.

## 2026-07-09 — eventsCount идемпотентность (вариант B, миграция)

**Проблема:** `eventsCount += packet.events.length` в SUBSEQUENT-ветке collect не идемпотентен — повтор одного пакета (retry после commit / двойной beacon / гонка) задваивал счётчик. `sessionsCollected` при этом чист (гейт `isFirstPacket && validatedTargetId`). Разведка показала: **в БД негде отследить обработанный (sessionToken, packetIndex)** — rrweb-события лежат только в S3 (`sessions/{siteId}/{sessionToken}/{packetIndex}.json`), в БД лишь `Session`-агрегат. S3 уже идемпотентен по ключу (PutObject перезаписывает). **Чистого фикса без миграции нет:** A (таблица событий в БД) — отмена S3-решения; C (conditional без хранилища индексов) — негде хранить; D (вычислять eventsCount из S3) — дорого/меняет семантику; E (гейт только retry) — частично, не покрывает двойной beacon. Все отклонены.

**Решение — вариант B** (предзаложен в DECISIONS 2026-05-03, теперь реализован): новая таблица `SessionPacketReceipt` — составной PK `(sessionToken, packetIndex)`, FK на `Session.sessionToken` `ON DELETE CASCADE`, индекс по `sessionToken`. В collect внутри той же `$transaction`: `INSERT INTO "SessionPacketReceipt" ... ON CONFLICT DO NOTHING` через `$executeRaw` → `eventsCount` инкрементится **только если receipt вставлен** (`rowsAffected === 1`). **Race-safe через unique-констрейнт PK** — та же природа атомарности, что overshoot-фикс через row-lock: два параллельных одинаковых packetIndex → один выигрывает INSERT, второй `ON CONFLICT → 0` → без двойного инкремента. Покрывает **оба** источника (retry + двойной beacon).

**Первый пакет — вариант (i) (единообразный).** `createMany` создаёт session с `eventsCount = 0`; наполнение идёт единообразно через receipt-гейт для ВСЕХ пакетов (включая первый). Один код-путь для eventsCount = нет щелей. Цена — один лишний крошечный `session.update` на первом пакете (0→len), на фоне createMany+S3+sessionsCollected это шум. RETRY первого пакета: createMany count=0 + receipt(idx) уже вставлен на первой попытке → `ON CONFLICT → 0` → инкремент пропущен, eventsCount не задваивается.

**endedAt — щели нет.** `endedAt` гейтится `!isFirstPacket && packet.isFinal` **НЕЗАВИСИМО** от receipt-гейта (пишется в тот же `session.update`, но по своему условию). Повтор финального пакета: receipt-гейт пропускает eventsCount-инкремент, но `endedAt` всё равно проставляется (условие истинно). Плюс он уже был выставлен первой обработкой. Финализация корректна во всех ветках. Подтверждено тестом: повтор final → eventsCount не растёт (6 не 7), endedAt остаётся set (не null).

**Миграция — ВРУЧНУЮ (важный факт про проект).** `migrate deploy` **НЕ в CI** (ни в deploy.yml, ни в Dockerfile — только `prisma generate`). Миграция применяется руками с локальной машины (`npm run prisma migrate deploy`, `DATABASE_URL` из `.env.local` → staging Yandex Managed PG). Порядок **БД→код**: таблица создаётся ПЕРВОЙ (аддитивный `CREATE TABLE`, на работающий старый контейнер не влияет), иначе новый код падал бы на `INSERT` в несуществующую таблицу. Cleanup: FK `ON DELETE CASCADE` авто-удаляет receipts вместе с сессией (retention-cron `cleanup-old-sessions`, удаление сайта) — retention-джоб не меняли, сирот нет (подтверждено тестом cascade).

- **Источник лога — платформа YC**, НЕ наш код: в проекте нет request-логирования, нет сторонних логгеров (morgan/pino/…), нет кастомного server.js, `next.config.mjs` без `logging`; строка появляется рядом с платформенным `START RequestID` и даже до готовности Next при cold-start. → **из приложения этот лог не отключить/не замаскировать** (пишется до/вне нашего кода; Next-middleware выполняется позже и не перехватывает).

**Тяжесть — УМЕРЕННАЯ:** site-token = право **ПИСАТЬ** трекинг (слать фейк-сессии, жечь budget цели), **НЕ читать** данные юзеров. Логи — YC Cloud Logging, **retention 72ч** (скользящее окно, дальше авто-удаление), доступ **внутренний** (`logging.viewer` на фолдере), не публичный. Не аврал, но нежелательно и усилится с ростом трафика.

**Корневая причина:** токен в URL — фундаментально слабое место (URL логируется везде: access-логи, прокси, Referer, история браузера). Затыкать один лог-источник бессмысленно.

**Решение (стратегия, НЕ реализовано):** убрать токен из URL → заголовок `X-Site-Token` (или тело). **Two-phase, строгий порядок:**
1. Сервер should-record принимает **header ИЛИ query** (backward-compat со старым закешированным tracker.js + `<script>` на academy). Деплой сервера.
2. Трекер шлёт `X-Site-Token` вместо query. Пересобрать/задеплоить `tracker.js`.
3. Дождаться вымывания старого tracker.js из кешей + обновления `<script>` на academy (координация с владельцем / Tilda).
4. **ТОЛЬКО ПОТОМ** ротировать `e464` → свежий токен, **никогда** не бывший в URL. Старые залогированные значения выветрятся за 72ч retention.

Нюанс: кастомный header на cross-origin GET → **CORS preflight** → добавить `X-Site-Token` в `Access-Control-Allow-Headers` (OPTIONS-хендлер в роуте есть).

**ВАЖНО:** «ротация e464» как отдельная задача **БЕСПОЛЕЗНА до фикса** — новый токен сразу начнёт литься в логи. **Порядок строгий: фикс token-из-URL → потом ротация.**

*(Побочно: pageUrl юзера с query утекает в тот же access-лог. Фикс token-из-URL это НЕ чинит — `url` остаётся в query should-record. Сейчас query обычно `utm_*` (низкий риск); если query юзеров станет чувствительным — рассмотреть отдельно, напр. слать нормализованный path вместо полного URL.)*

## 2026-07-14 — Кеш /tracker.js: НЕ immutable (опровержение мнимого техдолга)

**Контекст:** в ходе сессии всплыла гипотеза «tracker.js отдаётся immutable-кешем `max-age=31536000` без версии в имени → вернувшиеся юзеры держат старый бандл ГОД → не можем доставлять фиксы трекера → нужен content-hash в имени / тонкий loader / версионирование». Гипотезу собирались записать как техдолг. **Проверка данными её ОПРОВЕРГЛА — техдолга нет, в доки ложное так и не попало (не коммитили).**

**Факт (проверено живьём + логами):**
- `curl` на `https://staging.xn--90abjntggcss.xn--p1ai/tracker.js` → **`cache-control: public, max-age=0`** + `ETag` + `Last-Modified`. **НЕ** `immutable`, **НЕ** `31536000`.
- Условный GET с ETag → **`HTTP 304`**. Браузер ревалидирует на каждой загрузке; при immutable 304 не было бы вообще.
- В access-логах tracker.js: **41×200 + 6×304** — реальные браузеры ревалидируют.
- **Источник заголовка** — дефолт Next.js для `/public` (файл `public/tracker.js`, `next.config.mjs` пустой, без `headers()`). Content-hashed `max-age=31536000, immutable` в Next получают только `/_next/static/*` (там имя с хешем) — tracker.js там НЕ лежит.

**Следствие:** доставка фиксов трекера **уже работает оптимально**. Любой новый бандл долетает до вернувшихся юзеров на **следующей загрузке страницы** (ревалидация → 200 с новым телом), неизменённый отдаётся дешёвым 304. `content-hash` в имени / тонкий loader / `?v=hash` — **НЕ нужны** (решали бы несуществующую проблему; content-hash к тому же потребовал бы менять `<script src>` у всех клиентов на каждый деплой — хуже, чем сейчас).

**Опционально (не приоритет):** короткий `max-age` (5–10 мин) срезал бы даже per-pageload 304-round-trip. Микро-оптимизация с near-zero пользой при текущем трафике — не делаем.

**Урок:** заголовок кеша — проверять `curl`'ом, не из памяти/предположения (ср. с «Punycode всегда через node»). Мнимый «immutable-техдолг» родился из непроверенного предположения о дефолтах Next.

## 2026-07-15/16 — Инцидент: зависон S3-сбора (300с→504, потом 60с collect_timeout). Три гипотезы, две неверные

**ВАЖНО для истории — как эмпирика победила рассуждения.**

**Симптом:** первый анализ на реальных данных (6.3d) → **5 мин тишины → Gateway 504** (лимит 300с). Всё время ушло в `collectSessionsForAnalysis` (S3), **Claude не вызывался** (tok=0). Цель застряла в **ANALYZING** (markFailed не отработал — процесс убит СНАРУЖИ до любого catch). Локально dry-run те же 13 сессий = 3.1с.

- **Гипотеза 1 «деадлок пула сокетов»** (maxSockets=50 = concurrency 50) → **ОПРОВЕРГНУТА.**
- **Гипотеза 2 «платформенный egress не тянет параллель»** → **ОПРОВЕРГНУТА:** temp-роут `s3ladder` замерил getJson N=1/3/5/10/25/**50** — ВСЕ проходят (98-1041мс); `collectSessionsForAnalysis` целиком за **2364мс**; параллельный listKeys — 22-60мс. **Порога нет, код/concurrency в порядке.**
- **РЕАЛЬНАЯ причина: transient stale keep-alive сокеты.** `keepAlive:true` переиспользует соединения; YOS/egress молча роняет idle-соединение; следующий запрос берёт **мёртвый** сокет → шлёт запрос → ответа нет → **виснет молча**. Объясняет всё: интермиттентность, 0 ошибок, почему запись (putJson 1-за-раз) страдала меньше, почему после рецикла контейнера работает.
- **КЛЮЧЕВАЯ НАХОДКА:** `requestTimeout` в `@smithy/node-http-handler` **по умолчанию ТОЛЬКО ЛОГИРУЕТ WARN, НЕ обрывает запрос** — нужен **`throwOnRequestTimeout: true`** (об этом пишет сам ворнинг). Наш первый фикс был **декоративным**: логи показали 6 ворнингов, 0 обрывов, запрос висел дальше.

**Фиксы:** S3 `requestHandler` (`connectionTimeout 3s, requestTimeout 10s, maxSockets 64`, `3472eb0`) + **`throwOnRequestTimeout: true`** (ключевой, `35f68b9`) → зависший запрос обрывается за 10с → SDK ретраит на СВЕЖЕМ сокете → self-heal. + `withTimeout(60с)` на сбор с **markFailed** (цель не застрянет, `collect_timeout` 503, до Gateway-504). **Concurrency НЕ снижали** — доказано что 50 работают.

**УРОК:** три технические гипотезы, две неверные — спасла **эмпирика** (temp-роут, который ИЗМЕРИЛ вместо рассуждений). Если бы «пофиксили» по гипотезе (concurrency 10→3) — замедлили бы сбор в ~10× и **НЕ починили** реальную причину. Всегда мерить, а не гадать. *(Отдельный баг устойчивости: зависон оставил цель в ANALYZING навечно, т.к. процесс убит снаружи до catch — backstop cron в TODO.)*

## 2026-07-15 — LocalDateTime: время в зоне юзера, не UTC

**Симптом:** все timestamps в дашборде показывались в **UTC** (анализ 02:01 МСК → «23:01»). Применён в 3 местах (сессии-список, сессия-деталь, «Анализ от»). **БД остаётся в UTC (правильно).** Хардкод `Europe/Moscow` **отклонён** — РФ = 11 часовых зон, зона браузера корректнее.

## 2026-07-28 — Целевое действие через цели Яндекс.Метрики (Path M): Этапы 0–2

Продукт из «наблюдения о поведении» → конверсионный анализ: «сколько» берёт **Метрика** (число считает код, не AI), «почему» — из наших rrweb-записей. Целевое действие = цель Метрики, привязанная к `AnalysisTarget` (опционально; цель без него = прежний поведенческий анализ).

**Атрибуция B, отвергнута A (ГЕЙТ Этапа 0).** Разведка мерила `dimensions=ym:s:startURLPathFull` = страница ВХОДА (метод A). Это врёт: клик на странице X приписывается странице, с которой ВОШЛИ. **Формулировка «из открывавших страницу — N% за визит».** Строго отражает B и границу честности: для целей типа `action` Метрика в stat-API не говорит, на КАКОМ просмотре сработала цель → B = «открывал страницу И достиг за визит», НЕ «на этой странице».

**Остаточная неточность B (2A.4).** Инвентарь FullSnapshot'ов: соц/tel/mailto — в футере КАЖДОЙ страницы (22–36 соц-ссылок/стр); 16 CTA-кнопок шарятся между ≥2 целевыми страницами. Усиливать формулировку не потребовалось.

**Расхождение методик подсчёта — почему два слоя НЕЛЬЗЯ объединять в одну фразу.** Мы отсеиваем ботов своим способом (фильтр в should-record), Метрика — своим. Через полгода кто-нибудь попробует слить их в «3 из 24» — эта запись должна остановить.

**Состояние `mismatch` (Этап 2B).** Если у Метрики 0 визитов по странице, А У НАС записано >3 сессий — это НЕ «визитов не было» (наш матчинг/нормализация/расхождение методик), и врать клиенту «нет визитов» нельзя. `fetchGoalConversion` разводит: `no_data` (у Метрики 0 И у нас ≤3), `mismatch` (у нас >3, у Метрики 0 → в лог оба числа + оба фильтра exact/glob + период, для починки). Порог 3: 1–3 сессии Метрика может законно обнулить (короткий bounce до init), ≥4 против нуля — расхождение.

**Обрезка `URLPathFull` → truncation-safe матчинг (Этап 2B).** Метрика хранит путь обрезанным ~57 симв: `==` по полному длинному пути молча даёт 0 визитов при живой странице (доказано на `/tpost`). `fetchGoalConversion`: exact `==` → при промахе на длинном пути (>45) glob `=*'префикс*'` по безопасному префиксу; `matchedBy` (exact/glob) + число визитов логируются. Гейт `visits>0` + приоритет exact — молчаливый 0% невозможен.

Подтверждает системное расхождение знаменателей (см. выше «Расхождение методик»); скрытого 30-кэпа в коде нет.

**Расхождение знаменателей — ПРИЧИНА (правка Этапа 3, наблюдение опровергло прежнее объяснение).** Довесок 30/30 показал: Метрика **систематически ВЫШЕ** нас (22/33, 20/22, 30/42, 23/38). Прежняя запись («Метрика инициализируется через setTimeout 2000 → пропускает короткие визиты → выше должны быть МЫ») предсказывала обратное — эффект реален, но мелкий и перебит доминирующими:
1. **Бюджет-гейт (главное).** [should-record](app/api/tracking/should-record/route.ts) при `sessionsCollected >= sessionsBudget` возвращает `budget_exhausted` → трекер НЕ стартует → Session-строка не создаётся. Наш знаменатель **жёстко упёрт в `sessionsBudget`**, Метрика считает все визиты без ограничения. Эмпирика: Session-строки == `sessionsCollected` по всем целям (запись прекращается ровно на бюджете). На популярной странице с малым бюджетом разрыв растёт (30 записей vs 42 визита = бюджет 30, а трафик больше).
2. **Потери сбора.** Сессия существует только если долетел первый пакет: мгновенный отскок до flush, блокировка нашего `tracker.js` на кастомном домене адблоком (Метрику блокируют реже), fail-closed при таймауте should-record, сетевые дропы → визит есть у Метрики, Session-строки нет.
3. **Фильтр ботов.** Мы режем ботов агрессивно (`BOT_UA_PATTERN`), Метрика — своим способом.
4. **Визит Метрики ≠ наша сессия** по определению (визит склеивается по 30-мин таймауту, может охватывать несколько страниц; наша «сессия» = одна загрузка страницы).

**Ответ клиенту «почему 30 записей, а в Метрике 42 визита»:** наши записи — это **выборка под анализ, ограниченная бюджетом сбора цели** (останавливаемся на заданном числе, чтобы не жечь лимит тарифа), а Метрика показывает **весь трафик**. Это счётчики разного назначения. Именно поэтому конверсию берём из Метрики (полная популяция), а НЕ считаем «N из наших записей» — наши N это не весь трафик. Усиливает раздельность двух слоёв.

**Репрезентативность выборки под бюджет-гейтом (довесок Этапа 3).** Бюджет-гейт делает нашу выборку НЕСЛУЧАЙНОЙ: мы пишем **первые N сессий по времени**, затем `budget_exhausted` останавливает запись — выборка замораживается. Конверсию же берём из Метрики за период «первая сессия … вчера», который ПРОДОЛЖАЕТ расти. Итог: у capped-целей качественный слой («почему», наши записи) и количественный («сколько», Метрика) покрывают РАЗНЫЕ даты. Эмпирика academy (сбор растянут 7-13 дней, т.к. трафик низкий — бюджет НЕ за день): **home — 9 из 18 дней периода конверсии не покрыты записями** (записи 07-08..07-17, конверсия 07-08..вчера); **kabinet — 4 из 11**; tilda_free — 0 (совпало). То есть на home процент и объяснение относятся к почти НЕпересекающимся отрезкам времени — исчерпание бюджета за неделю, а не за день, не спасает: спасло бы совпадение окон, его нет. **Структурный риск ещё выше** для высокотрафичной страницы с малым бюджетом: бюджет выест за день → «почему» по одному дню недели/рекламному срезу, «сколько» по двум неделям. Каждое число честное, но рядом создают впечатление, что «почему» про тех же людей, что «сколько».

**Следствия:** (1) **промпт Этапа 4** должен сообщать модели, что выборка = первые N сессий окна сбора (по времени, не случайная) — не обобщать сверх данных, не переносить на другие периоды/срезы; (2) **кандидат на выравнивание** — считать конверсию за ОКНО СБОРА (min..max даты сессий), а не min..вчера, чтобы оба слоя покрывали одни даты (не реализовано — обсудить; сейчас период = min..вчера + trailing-fallback по Этапу 0); (3) в UI честно показывать окно записей рядом с периодом конверсии. Пункт (2)/(3) — отдельно, не в Этапе 4.

Формулировка (вариант A) — мягкая подсказка, не указание: «Если интересно, где она срабатывает, — можно проанализировать и {topOther}»; клиент волен анализировать текущую страницу (кейс «Вход: ЛК» на главной валиден).
