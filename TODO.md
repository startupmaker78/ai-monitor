## Собственный пикер целевого элемента (КРУПНЕЙШИЙ оставшийся вектор, не сейчас)

Записано 2026-07-31. Вырос из отрицательного результата: btn-цели Метрики
НЕ отдают пригодный селектор наружу (см. DECISIONS 2026-07-31 — API даёт
непрозрачный `btn_path=";AA"` + числовые хеши href/content, не XPath и не
литералы). Значит, детект «кто именно сконвертировал» через Метрику закрыт.
Но у нас есть ВСЁ СВОЁ, чтобы сделать это на своих данных.

**Идея:** юзер выбирает целевой элемент на НАШЕМ реплее сессии → мы храним
СВОЙ идентификатор элемента → детектим достижение цели в собственных
rrweb-записях (клик по этому элементу в записи = конверсия этой сессии).

**Что даёт:** per-session детект «эти 3 записи из 24 сконвертировали» —
- без Logs API Метрики,
- без getClientID / сшивки посетителей,
- без хранения идентификаторов посетителей (приватность),
- без зависимости от формата данных Метрики (свой пайплайн от и до).

**Как ложится рядом с Path M — ДВА НЕЗАВИСИМЫХ СЛОЯ, не заменяют друг друга:**
- Метрика (Path M, метод B) — «СКОЛЬКО» по полной популяции визитов.
- Свой пикер — «КТО ИМЕННО» из записанных нами сессий.
Оба нужны: у нас записана лишь выборка сессий, Метрика видит всех; но только
на своих записях мы можем показать САМО поведение сконвертировавших.

**Почему это реально (разведки уже проведены):**
- FullSnapshot страницы есть в каждой записи.
- node-map (rebuild) ~3мс — замерено, дёшево.
- клики приходят с rrweb node id (разведка A1).
- href стабильны при перегенерации вёрстки Tilda (разведка A6) — годятся как
  якорь; классы generic и НЕ годятся (Tilda их перетасовывает).

**Что предстоит спроектировать (оценка, НЕ реализация):**
- [ ] пикер элемента поверх нашего снапшота/реплея (выбор узла → наш селектор)
- [ ] форма хранимого идентификатора цели-элемента (по A6 — на базе href +
  устойчивых атрибутов, НЕ classList; продумать элементы без href — кнопки,
  не-ссылки)
- [ ] детект достижения в пре-процессоре (матч кликов сессии с целевым узлом
  по node id / нашему селектору)
- [ ] устойчивость к перегенерации вёрстки Tilda между записью цели и новыми
  сессиями (ре-матч по href-якорю, деградация когда элемент не найден)
- [ ] как показывать в UI: «N из M записанных сессий достигли цели» + связь с
  числами Метрики (не смешивать знаменатели — как весь Path M)

Записано развёрнуто намеренно: через полгода не восстанавливать логику заново.
Границы на момент записи: НЕ реализуем сейчас; сперва решение о приоритете.

**[P1 — завтра] gzip тела снапшота на collect.** FullSnapshot academy.
nolim.cc = ~2.92 MB (93% cap 3 MiB). Изоляция snapshot'а в свой
packet (commit ca5f4e7) спасает СЕГОДНЯ, но при росте контента —
снова 413 от YC-платформы до контейнера. Долгосрочный фикс: gzip.
Скоуп: клиент — `CompressionStream('gzip')` перед fetch/beacon +
`Content-Encoding: gzip` header; collect route — детект по header,
разжатие в `req.text()`, fallback для старого tracker.js без gzip
(backward compat). Побочная выгода: минус трафик клиента + минус
байт в S3 (packet.json сохраняется уже разжатый — оставить как
сейчас, gzip только на transport). См. DECISIONS 2026-07-08 «Трекер
изоляция FullSnapshot».

**[P2] Overshoot sessionsCollected.** Инкремент `sessionsCollected`
в collect транзакции не гейтится статусом цели: при N параллельных
первых packet'ах на почти-полной цели каждый успевает пройти
инкремент через свою transaction, пока auto-transition ACTIVE→READY
срабатывает только у одного (гейт `status="ACTIVE"` в updateMany
защищает переход, но не инкремент). Итог: budget пробивается на
`N-1` сессий выше предела. Улика — target
`cmrbt0a4j00002w3cp4smnhcs`: `6/5`, архивирован для расследования.
Фикс на выбор:
  (а) инкремент через updateMany с `where: {id, status: "ACTIVE"}` —
      concurrent старты после transition пропустятся;
  (б) явная проверка `sessionsCollected < sessionsBudget` перед
      инкрементом внутри той же транзакции — race-safe при row-lock
      на update.
См. DECISIONS 2026-07-08 «Данные: архив overshoot-target».

**[P2] eventsCount не идемпотентен на retry — участилось.** Известно
с DECISIONS 2026-05-03 как acceptable (telemetry-поле, а не billing).

дашборда, редкая, но при разборе учесть контекст retry.

- **[онбординг][дашборд] Нули в первый день после подключения счётчика —
  объяснить, а не показывать голые нули (2026-07-31).** Прошли путь клиента:
  подключаешь счётчик, всё верно (counter+token читаются по siteId, синк
  доходит, API отвечает 200), но главная показывает нули без единого слова
  почему. Клиент решит, что интеграция сломалась. Причина законная: синк берёт
  `date1=30daysAgo date2=yesterday` (`lib/metrika-client.ts`) — незакрытые
  сегодняшние сутки намеренно выбрасываются, а у свежего счётчика весь трафик
  как раз «сегодня» → в диапазон попадают только нули до следующего дня. На
  экране этой причины не видно. Сделать: когда у сайта нет НИ ОДНОГО снапшота с
  `visits>0`, а счётчик подключён недавно (например, site.createdAt или первый
  снапшот в пределах ~2 сут) — показывать на главной внятный статус вместо
  KPI-нулей: «Данные Метрики появятся после закрытия суток — ориентировочно
  завтра после 00:00 по времени счётчика». Отличать от «счётчик не подключён» и
  от «подключён давно, но реально ноль трафика» (там нули честные). Проверено на
  staging-сайте: 2 визита от 2026-07-30 висели невидимыми, пока 30-е не стало
  «вчера» и не прогнали синк. Это увидит КАЖДЫЙ новый клиент в первый день.
  Границы: только UI/сообщение, диапазон синка (`date2=yesterday`) НЕ трогать —
  выбрасывать незакрытые сутки правильно.

- **[низкий приоритет, ~15 строк][цели] url-mismatch для мультицели — НЕ делаем
  сейчас, осознанно (2026-08-03).** Бейдж «эта цель про другую страницу»
  (`goalWarning` в `goal-select.tsx`) показывается только для `type==="url"`. У
  мультицели (`type:"multi"`) url-условия лежат в `children[]`, до них код не
  доходит → бейдж не показывается, даже если ребёнок-url про другую страницу.
  Это НЕ баг и НЕ падение (проверено: `conditions[0]` читается только под
  `type==="url"`, multi/param не роняют). **Почему намеренно молчим:** мультицель
  по смыслу = «целевое действие любым способом»; часть детей может быть про эту
  страницу, часть про другую — показать mismatch в такой ситуации запутает
  сильнее, чем промолчать. Если когда-нибудь понадобится: вытащить url-условия
  из `children` в `fetchMetrikaGoals` и показывать mismatch ТОЛЬКО когда ВСЕ
  url-дети про другую страницу (~15 строк). Через месяц не переоткрывать без
  этого обоснования.
